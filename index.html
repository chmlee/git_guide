Collaborating on Data Analysis Project with Git

1 Introduction

The goal for this guide is to introduce version controlling with Git in the context of collaborative data analysis projects.

The guide was initially a quick start guide for my Causal Inference group project. Since I was the one who proposed we use Git for collaboration, I wanted to write a step-by-step guide to make the adoption easy. Turns out I grossly underestimated the difficulty of writing the guide, and couldn’t complete it before the project deadline. It has now evolved into a more comprehensive introduction of Git.

Why yet another Git tutorial, while the internet has no shortage of posts on the same topic? What makes this guide different?

  1. This guide contains crash courses on some fundamental programming/computer concepts. Many Git tutorials assume a significant amount of knowledge on programming, and is not approachable for those early in their coding journey. A common approach is to simply instruct readers to copy the commands, paste them to the terminal, press <Enter>, and voilà, you get the desired result. But (1) you should never run random commands from the internet without understanding what exactly they do, and (2) you have to known them sooner or later, so why not now?

2 Why Git

Git is a version control system (VCS) that help tracks changes made in text files. It is commonly used in programming to manage changes made in source code, but can also be applied to other file formats2, such as Markdown, CSV, etc.

2 In theory Git can also track changes made in non-text files, such as compressed files (e.g. Microsoft Word documents) and binary files (e.g. SQLite file), but dedicated VCS for these specialized file format is usually preferred over Git. The reason would be apparent later.

2.1 Version Control

If you have worked on a non-trivial project involving multiple files that went through several iterations, the following directory structure should look familiar:

my-project/
├── data/
│   └── data.csv
├── report.Rmd
├── report-20250101.Rmd
├── report-20250201.Rmd
├── report-20250301.Rmd
├── report-final.Rmd
├── report-final-update-intro.Rmd
├── report-final-version-2.Rmd
├── report-final-version-3.Rmd
└── report-final-version-4-final-final.Rmd
Crash Course on Directory

Another name for directory that people may be more familiar with is “folder”. While there may be some minor differences between the two3 , the distinction is not important for the purpose for this tutorial. Most technical documents use “directory,” so that’s the term I would stick to.

Directories are usually represented in tree structures. The above example reads:

  • Directory my-project/ has 10 children: 1 sub-directory data/ and 9 files in the form of report.Rmd and report-xxx.Rmd
  • Directory data/ has exactly one child – file data.csv.

We say my-project/ is the working root directory of this project. Everything concering the project is inside this directory.

Slashes (/) are added at the end of directories’ names (my-project/, data/) in the text representation above. This is done to distinguish between a directory and a file.

We can also use / to specify the path of a file or a directory. The path for report.Rmd is my-project/report.Rmd, and the path for data.csv is my-project/data/data.csv.

Note that in practice Windows use back-slashes (\) instead of /, so the examples should be rewritten as my-project\report.Rmd and my-project\data\data.csv if you are using Windows. In most cases Windows should be able to understand both notations. MacOS and Linux use / natively, and this is also what this tutorial use.

There are three special paths:

notation meaning
./ current directory
../ parent directory
/ system root directory

(On Windows they are .\, ..\ and \ respectively, but as mentioned you can substitute \ with / in most cases.)

If you are located in my-project/, the relative path for report.Rmd would be ./report.Rmd – starting from my current directory my-project/, look for report.Rmd. Similarly, the relative path for data.csv would then be ./data/data.csv – starting from my current directory my-project/, look into directory data/, then locate file data.csv.

If you are located in data/, the relative path for report.Rmd would be ./../report.Rmd – starting from my current directory data/, go to its parent directory my-project/, then locate file report.Rmd. data.csv, on the other hand, is much simpler – ./data.csv.

You do not need to explicitly specify ./. So ./report.Rmd can be written simply as report.Rmd, and ./../report.Rmd is equivalent to ../report.Rmd.

System root directory /, sometimes simplified as root directory, is the root directory of your system (duh!). Every file and directory on your system is a child or descendant of /. Paths starting from / are absolute paths. Say my-project/ is located at /home/louis/Document/class/causal_inference, the absolute path for data.csv would then be /home/louis/Document/class/causal_inference/my-project/data/data.csv.

Relative paths or absolute paths may be preferred depending on your use case. The rule of thumb is use relative path if it is project specific (“this file reads data from a sibling directory”), and absolute path if it is system-wide (“use R version 4.5.1 on the system to run this script”).

People used to graphical user interfaces (GUI) may find this unnecessarily abstract. Why not just open File Explorer then point and click?

Firstly, it’s easier for technical document writers to include a text representation of the directory structure than taking screenshots of File Explorer. Secondly, many tools only provide command line interfaces (CLI) – you type commands in a terminal – and the arguments are expected to be text. While Git does provided basic graphical user interfaces, and there exist third-party tools that provide more advances interfaces, we will start with CLI.

Understanding path and directory is crucial to programming and development, and messing up basic concepts can lead to irreversible consequences. My favorite example is rm -rf /my-project vs rm -rf / my-project. rm -rf deletes everything is the path provided by the next argument. So the first command deletes everything in /my-project, while the second one delete everything in / (note the space between / and my-project!) which is… everything in your system!

This exact mistake happen surprisingly often.

It is also a reminder you should never blindly run commands found on the internet or produced by AI.

You are working on your report, and are instructed to submit your draft to your supervisor on the first day of each month. For each submission you append your report name report.Rmd with dates (e.g. report-20250101.Rmd)

In April you are ready to submit your report and name your latest iteration report-final.Rmd. But your supervisor is not satisfied with your intro and asked you to make some major changes. You update your report, name this new report report-final-update-intro.Rmd to indicate what you’ve change. But of course this is not the only changes you are asked to make. You ditched your previous naming scheme and give each iteration a version number, e.g.  report-final-version-2.Rmd, until you reach version 4 and name it report-final-verions-4-final-final.Rmd.

This work flow is not optimal. First and foremost, you store multiple copies of the same file which is not only confusing but also taking many disk space. For each iteration you create a new copy of the report regardless of the amount of the changes. You may have only changed a few characters, still a near-identical duplicate of the file needs to be created. It is also not obvious what the differences between each versions are. You can be disciplined and enforce consistent naming schemes (report-final-update-intro.Rmd), or maintain a changelog recording what has been changed between iterations (version 3: fixed x-axis in graph 4.1 and 4.2) , but they add more overheads and complexity to your workflow.

Introducing Git, a piece of software to make versioning simple 4. Instead of saving multiple versions of the same file, we save snapshots of each iterations, also known as commits.

4 Simple, not easy. While the underlying architecture may be simple, (every git operation is either creating some objects or moving HEAD!) it has quite a learning curve and not an easy tool to master.

Consider a todo list todo.txt that went through two iterations of changes

Version 1:

grocery:
  apple
  banana

Version 2:

grocery:
   apple
   banana
   orange

add orange to list grocery

Version 3:

grocery:
  banana
  orange
clean:
  dishes
  laundry

remove apple from grocery, and add a new list clean

With our primitive manual version control system, we would store three versions of the todo list:

todo/
├── todo-version-1.txt 
├── todo-version-2.txt 
└── todo-version-3.txt

With Git, only one todo list is visible to user at a time, Every time we make changes to todo.txt and commit the changes, Git takes a snapshot of the file content and save it in a special storage5.

5 We’ll explain what exactly this “storage” is. For now, just think of it as a special place where Git stores everything.

todo/
└── todo.txt

Let’s go through a very simple Git workflow.

First, we create todo.txt, then add apple and banana to grocery list. Then we commit the changes with Git, and get commit C1. The commit points to version 1 of the file in storage.

Next we add orange to list grocery. We iterate over commit C1 and get commit C2, which points to verions 2 of the todo list in the storage.

Finally, we remove apple from grocery, and add a new list clean. Again, we iterate over commit C2 and get commit C3, which it points to version 3 of the todo list.

Think of Git as a time machine. We can freely travel between commits, and depending on what commit we travel to, Git points to the corresponding version of todo.txt.

At any given commit, you see exactly one todo.txt, but the content changes accordingly.

While Git does create new copies of todo.txt for each snapshot, it also compress them so that it take up less disk space.

Furthermore, Git doesn’t always create new copies for each snapshot. To illustrate this, let’s revisit our my-project example. A naive version control system would create new report.Rmd and data.csv for each commit:

  1. Next we commit the updated report.Rmd (version 2) to C2, as well as data.csv. Note since no changes are made to data.csv, it is still at version 1.

  1. Finally, for commit C3, we committed the updated report.Rmd (version 3) and the unchanged data.csv (version 1).

(Review the above Git history to see how commits are made step-by-step)

Each commit points to two files in the storage, report.Rmd and data.csv. Recall that in this example, all changes are exclusively made in report.Rmd, while data.csv remained unchanged (as raw data should). We are storing three identical data.csv that hasn’t been changed since commit C1!

To fix this, Git simply keep one copy of data.csv in it’s storage, and points all three commits to this data.csv:

View Full Git History
  1. First we commit report.Rmd (version 1) and data.csv (version 1) in commit C1.

  1. Next we commit the updated report.Rmd (version 2) to C2. Note that since no changes are made to data.csv, instead of creating an identical data.csv, commit C2 simply points to the one that commit C1 created.

  1. Finally, for commit C3, we committed the updated report.Rmd (version 3), and points to the same data.csv commit C1 created.

Let’s hop back to our time machine and see how it behave this time.

If we travel to commit C1, we see version 1 of Report.Rmd and data.csv.

When we travel to commit C2, we see version 2 of report.Rmd, but version 1 of data.csv.

When we travel to commit C3, we see version 3 of report.Rmd, and version 1 of data.csv.

This is known as immutable snapshots. While users do mutate the files, Git never mutate files in its storage. If Git detect changes made to the files, it add the new file to the storage. If not, it simply points to the old one.

2.2 Diffing

Immutable snapshots makes comparing commits straightforward. We often want to track the changes made to a file throughout its development phases, and to do so Git can simply compare the files each commit points to and summarize the changes. This is known as diffing.

Consider the todo.txt example. Comparing commit C3 to C1 is simply comparing todo.txt version 3 to version 1.

Git will run a special programme to compare the two files, and calculate the steps to turn todo.txt from version 1 to version 3. Eventually Git would produce a diff that looks like:

 grocery:
-  apple
   banana
+  orange
+clean:
+  dishes
+  laundry

Lines that were removed are denoted with minus sign - and those that were added are prefixed with plus sign +. The diff above shows that we remove the line containing apple, and add the line with orange, as well as the 3 lines involving clean.

Note that file diffing is line-based – a change operating is either removing or adding a line. There is no “change line \(i\) from \(A\) to \(B\)”.

Say we change banana to banaan, our diff would look like:

 grocery:
   apple
-  banana
+  banaan
   orange
 clean:
   dishes
   laundry

Git couldn’t tell we swapped the last two characters for banana. All it can say is we deleted the line containing banana, and added another line containing banaan.

Things get more interesting when commits contain more than one files. Let’s revisit my-project example. To compare commit C3 to C1, Git first look at report.Rmd version 3 and version 1, then calculate the difference as usual. Next it move on to data.csv, and found both commits points to the same file in the storage. No diffing is required for this file!

2.3 Feature branches

Code should be organized based on their functionalities. Instead of writing everything in one single file, it is a good practice to split them into smaller chucks of code across several files. It’s much easier to understand what four 500-line sections of code are doing than to read through the entire 2,000 lines at once.

Consider the following data analysis project.

my-project/
├── data/
│   └── survey.csv 
├── results/
│   └── clean_survery.csv
├── clean.R
├── model.R
└── report.Rmd

This structure separates codes according to the different phases of data pipeline:

  1. Clean data: clean.R reads and cleans raw data survery.csv, and generate a new dataset clean_survery.csv.
  2. Build models: model.R reads clean_survery.csv and perform statistical analysis.
  3. Present findings: report.Rmd contains the full report where we introduce are analysis method and import models from model.R.

Assuming our workflow is perfectly linear, that is, for each iteration, we only add new files and never revise what we have written. Our Git history would look like:

  1. We start with only the raw dataset survery.csv in commit C1.

  1. We write clean.R that takes survey.csv as an input, clean it, and output clean_survey.R. Commit C2 points to the newly added clean.R and clean_survey.R, as well as survey.csv from the previous commit.

  1. We build our models in model.R.

  1. Next, we build our models in models.R where we take clean_survey.csv as an input. Commit C3 now points to the new file models.R and all the files from previous commits.

  1. Finally, we work on our Report.Rmd where we explain our methods and import models from models.R to illustrate our analysis result. Commit C4 points to the new Report.Rmd and all files from previous commit.

But this is rarely the case. We sometimes go back and forth the pipeline, and make changes to files that were previously committed.

A more realistic workflow may look like this:

  1. Next we clean the raw data with clean.R and output clean_survey.csv.

  1. We build are models in model.R.

  1. For report.Rmd, we first specify our methods, then import models from model.R.

But wait! The model shows the average age for student mean(age) to be 95.3. Something is not right. Upon inspection we discover some missing values in the raw data were coded 999 instead of NA, and we failed to convert them properly during cleaning. We have to update clean.R and regenerate clean_survey.csv.

First we save what we have for report.R – the models we imported may be incorrect, but we don’t want to toss away what we have wrote.

Then we make the necessary changes to clean.R and regenerate clean_survey.csv. Since both files are modified, commit C5 no longer points to version 1 of clean.R and clean_survey.csv, but the updated version.

  1. Before jumping back to report.Rmd, we decide to try a new model. Constant correlation doesn’t seem to be a realistic assumption, so we test more flexible structures, and decide to settle with an autoregressive one. We update model.R, and commit the changes.

  1. Finally, we complete report.Rmd

If we look closely what files are changes in each commit, we notice that only a few are changed at a time. And thanks to our modularized codebase, these changes corresponds to one of three themes: data cleaning, model building and writing report.

Can we also modularize our git workflow by categorizing commits based on their functionalities?

To do so, we need to create git branches. When you first create a Git project, also known as a Git repository (or repor for short), all our commits live in the default branch - the main branch. To modularize our commits like we do with the code files, we have to create new branches and diverge from the main branch. All our new changes would be isolated in the new branches without effecting main. We merge the changes from the new branches back to main once we feel ready.

If commits living in the same branch can be seen as snapshots of a timeline, then different git branches are like parallel universes reflecting alternative states of that timeline. All branches reflect a alternative version of the main timeline, each containing slightly different changes, usually grouped by a common theme.

Similar to files, our commits can also be classified into three main themes: report writing, data cleaning and model building. Therefore we create 3 branches: report writing, data cleaning and model building, and our Git workflow may look something like: a
